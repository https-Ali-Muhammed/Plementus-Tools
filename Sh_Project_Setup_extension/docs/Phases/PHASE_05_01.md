## Contract v1

[`contract.mjs`](../../src/adapters/contract.mjs) exports v1 constants and three pure validators. Future Odoo.sh, customer Odoo and Plementus adapters use the same shape, with a distinct `provider` discriminator. Provider-specific UI, selectors and actions belong to later versions/adapters. Unknown versions, fields, operations not matching a declared capability, and malformed values fail with a generic error. No function performs an action or persists data.

- Capability: `{version, provider, operation, classification, mutates}`. `supported` means the adapter declares the operation; `unverified` means its behavior is not established; `blocked` means it cannot be used. This classification is independent of evidence tier.
- Request: `{version, operation, parameters, target, context, approvalReference?}`. `target` has provider, opaque sanitized reference and environment; `context` has run and step handles. All handles use bounded lowercase token syntax, not actual customer/account/repository names, URLs or credentials. Parameters are at most eight bounded boolean or integer flags (0–1000); no free text. Mutations require an `approvalReference`, which is only a correlation handle, **not operator identity or authorization proof**. All target/account/repository context remains volatile and is excluded from SEC-01 checkpoints.
- Result: `{version, operation, target, status, evidenceTier, category, retrySafety, reviewRequired, reconciliationRequired, verification}`. `observed` means reported state was observed, not merely clicked; a write additionally needs `provider-state` verification and the matching live demo tier. `manual-attestation` is an operator claim and must use `MANUALLY_ATTESTED`; it is never provider verification. `unknown` means no reliable outcome; `blocked` means action cannot proceed; `failed` means a known failure. `category` is a fixed redacted code, never raw evidence or an exception. `verification` is `none` or `provider-state`. The validator checks claims, but cannot prove that a caller actually observed a provider.
- `retrySafety`: reads are `safe` for a future bounded retry policy; writes are `unsafe` for automatic retry. An `unknown` write is `reconcile-first`, sets `reconciliationRequired`, and must be inspected before a fresh approval. Every non-observed result and every write sets `reviewRequired`. `unverified` capability permits only `unknown`/`blocked`; `blocked` permits only `blocked`. No v1 live evidence tier exists for customer Odoo writes, so v1 cannot mark one observed.

For a mutation, `timeout`, `interrupted`, and `unknown-outcome` categories require `unknown`, operator review, and reconciliation before retry. `failed` remains available for definite pre-write failures such as `permission`. Parameter validation rejects every hidden, accessor or symbol property before reading values; every admitted flag is an enumerable own data property checked against the bounded boolean/integer rule.

`SIMULATED` and `LOCAL_BROWSER_TESTED` cannot verify a provider write. Odoo.sh and Plementus demo tiers are bound to their matching provider; the GitHub sandbox tier is invalid for these site adapters. No credential, session, customer identifier, raw exception or result body is part of the result schema. Callers must independently verify target, page, actual operator approval and provider state before making a corresponding claim.
