## 2. Exact types, budgets and validation

All data schemas below are closed: every listed key is required, no other string or symbol keys, no optional keys or implicit defaults. Alternatives explicitly use `null`. Records have exactly `Object.prototype` or null prototype and own enumerable data properties only; inherited data never supplies a field. Reject accessors without invoking their getters, functions in data, symbols, undefined, bigint, non-finite numbers, exotic objects, cycles, sparse arrays, aliases between records in a payload, and unexpected depth. Arrays are allowed only for `results`; exactly dense index `0` and ordinary `length`, no extra own keys, when valid. A missing/multiple result is an error, not a partial result.

`ID`: primitive string, 1–128 printable ASCII bytes U+0020–U+007E, no trimming/coercion. The synthetic corpus uses no whitespace, secrets or URL-shaped IDs; printable space alone does not authorize a new identifier. `N`: primitive nonnegative safe integer, maximum 9,007,199,254,740,991; `P`: positive `N`. This representational ceiling specifies the required bounded sequence, not a new resource allowance. No wraparound; before an increment would exceed it, close the instance with `sequence_exhausted`. `Time`: `N` milliseconds from the injected mock clock. `Role`: exactly `plementus`, `github`, `odoo-sh`. A role may be `null` only where explicitly stated. `PageKind`: exactly `supported`, `unsupported`, `unknown`.

| Resource | Owner-approved R0 P6 limit, unchanged |
|---|---|
| Role/page-kind | Exact enums above; longest 9 / 11 UTF-8 bytes |
| Operation/reason | Fixed enums in section 3; maximum 32 ASCII bytes each |
| Opaque identifiers | 1–128 printable ASCII bytes |
| Private synthetic origin | 256 UTF-8 bytes |
| Private synthetic full URL | 2,048 UTF-8 bytes |
| Review-intent envelope | 1,024 UTF-8 bytes |
| Mock result envelope | 4,096 UTF-8 bytes |
| Public result/summary envelope | 512 UTF-8 bytes |
| Record complexity | At most 16 own fields per record, depth 2 with root record at level 1; at most one result-array element |
| Live resources | Three role slots, one unassigned capture, one pending read globally; no queue/history |
| Capture deadline | 60,000 ms from capture, non-renewable through confirmation/read |
| Observation deadline | 5,000 ms end to end from admission, including boundary invocation and completion |

Record depth counts records, not the `results` array container: root envelope is level 1, its sole result record level 2. Array objects still reject extra own fields. Private records in section 7 are separate flat records, not nested inside one serialized state object. Native function/connection/promise/timer capabilities are private closure handles, never data fields to traverse or serialize.

Byte accounting: string limits use UTF-8 encoded bytes. Envelope limits use UTF-8 bytes of compact JSON of validated copies, in schema key order as listed below, with no indentation. Escapes count as serialized, e.g. a quote needs two JSON bytes; envelope and scalar limits both apply. Reject lone UTF-16 surrogates. Validate descriptors, own keys, enums/types, depth and field byte sizes before constructing the compact JSON; never serialize caller objects or invoke their `toJSON`, getters or conversion hooks. Use an own-data copy with null prototype and no inherited serialization hooks. Unknown values/keys and oversize input are rejected, never truncated, normalized, repaired or partially admitted. A per-field maximum is not a promise that all maxima fit the aggregate envelope.

Reflection on a hostile Proxy can throw or reenter. Treat it as a boundary: catch without exposing the error and recheck terminality/generation before any mutation. Descriptor inspection does not promise that Proxy traps never execute, nor a CPU/memory sandbox for arbitrary JavaScript. Test inputs are controlled synthetic objects. No arbitrary caller code or hostile real pages are executed under R1.

`limits` is a closed, flat configuration record with exactly these 15 keys/values: `codeBytes:32`, `idBytes:128`, `originBytes:256`, `urlBytes:2048`, `intentBytes:1024`, `resultBytes:4096`, `publicBytes:512`, `maxFields:16`, `maxRecordDepth:2`, `maxResultItems:1`, `maxRoles:3`, `maxCaptures:1`, `maxPending:1`, `captureMs:60000`, `observationMs:5000`. Validate and copy once; no externally mutable configuration reference remains. Any missing/different value is `setup_invalid`, never a configurable policy override. The ID minimum and enum limits are fixed schema rules.

Only `confirm`, `observe`, `cancel`, `manual` are review-intent operations. `complete` and `timeout` are internal events, not exported admission endpoints. Invalid operation strings are never echoed; the public `operation` uses the called method's fixed operation, or `invalidate` for an invalid trusted invalidation event. Factory: `createReadOnlyAdmission(boundary, limits)`. It returns one private owner controller with `captureInvocation(tab)`, `attachReview(sender, connection)`, `confirmSelection(connection, intent)`, `observeOnce(connection, intent)`, `cancel(connection, intent)`, `manual(connection, intent)`, `invalidate(event)`, `snapshot()`. Explicit cancel/manual entry points refine the earlier candidate API; they add no product message handler. No public completion or restore method exists.

Only the trusted synthetic harness holds capture/attachment/invalidation methods. Its review mock receives only the four intent methods and a private ticket callback. This is a test dependency boundary, not an authentication mechanism against arbitrary code in the same JavaScript process. Nothing imports the controller into the extension product.

`boundary` is a closed descriptor-validated configuration with exactly `bootId` (one fixed boot string), `now` (function), `schedule` (function), `clearTimer` (function), `read` (function), `deliverTicket` (function). Copy function identities once. Function-valued fields are allowed only here, never inside data records. Invalid setup returns a permanently CLOSED controller with `setup_invalid` results; it must not invoke an invalid boundary or expose exceptions. No constructors, dynamic module names or strings of code are accepted.

Ticket holders cannot choose code, permissions, a URL, a read target or an evidence tier.

Internal completion/timeout observations in the transition table describe events, not a second externally admitted result. Other methods are synchronous. The public observation Promise settles exactly once with its first terminal result, even if the underlying Promise remains unsettled. Settling the public Promise or clearing pending admission never proves underlying completion or releases capacity for a new read. Invalid connection/intent calls return a resolved rejection Promise from `observeOnce` without invoking `read`.

Public record (15 fields, listed in order): `operation:Operation`, `outcome:Outcome`, `reason:Reason`, `state:State`, `role:Role or null`, `pageKind:PageKind`, `sequence:N`, `plementus:empty/supported`, `github:empty/supported`, `odooSh:empty/supported`, `evidenceTier:"SIMULATED"`, `accountVerified:false`, `executionAuthorized:false`, `approvalGranted:false`, `trustedContinuingContext:false`. Authority flags remain false on every success, refusal, terminal result and snapshot.

Public role summaries are three independent historical enum values, not atomic/fresh context. `snapshot()` returns `outcome:snapshot`, `operation:snapshot`, `role:null`, `pageKind:unknown`, current state/revision/summaries and last terminal reason or `ok`. It performs no read and grants no authority. Manual intent means a request for manual fallback, not a reported completed operation; this API accepts no attestation payload. When the controller is CLOSED, manual fallback remains an external, non-authorizing instruction/outcome based on its terminal result; calling `manual()` cannot reopen it or issue a ticket. Any separately authorized human report must remain MANUALLY_ATTESTED outside this API, never successful observation/approval.

## 6. Correlation, provenance and one-use admission

1. Start empty with immutable boot ID and private instance identity. A real Chrome callback is neither required nor fabricated. The owner-only capture method is the sole synthetic invocation source; a review's claim of invocation is an unknown field and rejected.
2. Attach a validated review sender and fresh connection by the trusted boundary. No caller-supplied generation is authoritative. Same current connection/pair is a duplicate (`replayed_intent`); a retired connection cannot be reattached. Because only two review connections belong to a test scenario, the harness must never reuse them; the controller also rejects a sender matching the immediately retired pair. Additional attachments require a separately initiated test scenario, not an unbounded retired-owner registry or automatic replacement controller. If a valid review replacement would terminate an unsettled underlying read, close the current controller instead: do not install the new owner or issue its ticket.
3. Issue one current ticket on attachment (captureId `none`), capture, confirmation and read admission. Each issuance increments `intentSeq` and replaces the previous ticket; only equality to current sequence is eligible. A consumed/lower sequence is replay; a larger/wrong generation/capture is mismatch. Accepted confirm/observe/cancel/manual consumes its ticket before any boundary callback. Stale or wrong-connection traffic never invalidates the current owner's work. Successful completion clears its ticket and publishes no new ticket: another observation requires a fresh private capture. Ending the review remains possible through trusted review_lost, including when no ticket exists.
4. Capture validates/copies the six target fields and stamps `capturedAt` before publication. One unassigned capture only. Capture of a different unused role's fixed tab after a completed observation retains the previous inert summaries. Capturing a tab already summarized, or recapturing with a live capture but no unsettled underlying read, first globally invalidates the old capture/admission/summaries, advances generation, then accepts the fresh capture if valid. A recapture affecting an unsettled underlying read instead closes the controller with target_changed and does not accept the new capture. It never automatically confirms/reads. Invalid capture data causes MANUAL fallback only when no underlying read is unsettled; otherwise the same failure closes the controller.
5. Confirmation requires the current private capture, current owner/ticket and explicit role matching the fixed target tuple. It changes CAPTURED to CONFIRMED and sets the selected role. It does not create a read or renew time. Duplicate roles or wrong role/tab mapping fail closed. Three role summaries can only be obtained from three separate explicit confirmations and reads on distinct synthetic tabs; no inference from URL, title or fixture signature assigns a role.
6. Observation requires CONFIRMED, matching selected role, current unused ticket, no pending admission and no unsettled underlying read, and unexpired capture. Reserve pending identity, increment request sequence, and mark READING before invoking `read(copiedFrozenRequest)`. Issue a new ticket for cancel/manual while reading. Recheck current pending identity after ticket delivery and timer setup, immediately before invoking read; if either invalidated the attempt, do not call read. Set `readPhase:IN_FLIGHT` immediately before entering the boundary function, so a cancellation reentered from inside that function also closes permanently. At most one underlying read may be initiated per controller at a time; no retry/replay/queue. A competing observe returns `busy` without clearing the valid pending read. A subsequent read is eligible only after an earlier underlying settlement has actually been observed by its current handler and its admission has terminated, while the controller remains non-CLOSED.
7. `read` must return a same-realm native Promise. Synchronous throw or invalid return after invocation cannot prove that no underlying work escaped: close permanently with boundary_threw or boundary_shape. A native rejection observed by the current handler is settled and ends the attempt with boundary_rejected. Never accept an arbitrary thenable or read its `then` getter. Attach handlers using captured native Promise operations; recheck generation after any potentially reentrant boundary. If read returns a native Promise after a reentrant closure already occurred, attach only inert fulfillment/rejection sinks; never re-register it as pending or reopen admission. The trusted test boundary itself is executable test code, not an untrusted sandbox.
8. A completion can be admitted only through the closure associated with the exact pending entry. Check CLOSED/retired status and entry/owner/instance/generation before any mutation or payload inspection. A current native settlement handler then sets `readPhase:SETTLED`, checks all envelope IDs, the sole result's captured tab/window/frame/document/origin/URL, capability and page-kind, then clock/deadlines and current state again immediately before consume. There is no result admission by copied request ID alone. A document changed with identical URL fails. Missing lifecycle evidence is not silently inferred; changes known to the harness are explicit invalidation stimuli, not real event coverage.
9. Consume/clear pending and capture, invalidate its ticket, cancel the timer and discard private comparators before publishing a terminal result. Valid settled `supported` with `available` produces one `observed` result and that role's inert summary; a settled `unsupported`, `unknown`, denied/unsupported capability or malformed/rejected result enters MANUAL and clears all summaries. A termination while readPhase is IN_FLIGHT instead sets readPhase RETIRED and state permanently CLOSED, clears all owner/capture/admission/summary data and settles the public observation result with the first terminal reason and state CLOSED. This includes cancellation, manual request, timeout, target/review invalidation, review replacement, recapture and current-owner faults. Later underlying settlement is discarded without inspecting payload, mutating even readPhase/revision/lastReason, issuing a ticket, notifying again or reopening. No result represents continuing freshness or account identity.
10. On any reentrant or asynchronous return, first preserve the earliest terminal decision. While dispatch/validation is active, other mutating calls return `busy`; trusted invalidation can terminate immediately, and snapshot may read a sanitized copy. Such invalidation cannot be overwritten by an outer success/throw handler. `deliverTicket`, `read`, `now`, timer scheduling/clearing and reflective validation all require these guards. Review harness actions occur after delivery returns, not synchronously inside `deliverTicket`.

Closure handles: one current connection, one immediately retired connection, one underlying native Promise handle, one distinct public-observation resolver, one timer handle, one current frozen ticket, immutable boundary function references/limits and immutable private instance token. Read lifecycle is NONE → IN_FLIGHT → SETTLED for an observed settlement, or IN_FLIGHT → RETIRED on early termination. SETTLED may become IN_FLIGHT only for a later independently captured/confirmed observation on this still-open controller. RETIRED is irreversible and implies CLOSED; a native Promise already physically settled but whose handler has not yet run is conservatively IN_FLIGHT. Pending admission and native-read lifecycle are separate: null pending/public settlement cannot change readPhase or authorize another read.

At terminal consumption, clear controller-owned capture/pending/comparison cells, request references, ticket and timer before publishing the public terminal result; release the public resolver after settling it once. Handlers use clearable comparison cells, not captured URL/origin copies. On retirement, discard the controller's underlying Promise reference; leave only the immutable closed disposition and inert sinks needed to absorb any later settlement. No drain queue, retained-read list or replacement handle exists. Only owner identity/connection and bounded counters plus up to three enum summaries survive successful settled completion. MANUAL/CANCELLED may retain an owner for explicit fresh capture only when no unsettled read was affected. CLOSED clears all owner/retired identities, summaries and operational handles, cannot accept captures/reviews/observations, and has no reset/reopen path.

The externally held Promise, boundary request copy or queued reaction may outlive these cleared references. JavaScript reference cleanup does not guarantee physical cancellation, garbage collection timing or memory erasure; the controller must not claim otherwise. At most one retired underlying read can remain associated with this permanently closed controller because it can never initiate another. External manual fallback remains non-authorizing. Creating another controller is not an automatic retry/recovery mechanism; this per-controller rule provides no cross-instance browser-operation bound or production cancellation guarantee.

Terminal rows consume pending admission before notifying any external callback; admission rows instead reserve it before calling the boundary. “Clear” means capture, pending, ticket, timer and all summaries unless a row expressly retains summaries. Each accepted capture/review replacement/global invalidation advances generation and synchronizes any surviving Owner.generation; every accepted mutation increments revision. Ordinary confirm/read advances ticket sequence without renewing capture time; success clears the ticket. `terminalLatched` records the first terminal outcome/reason and is not set by intermediate capture/confirmation/admission. It may clear only on a later explicit enabled capture/attachment on a non-CLOSED controller, never by late settlement. For early termination of IN_FLIGHT, set CLOSED/RETIRED, latch the first reason and clear admission before cleanup callbacks; those callbacks cannot replace it. Settled success is published only after cleanup; a cleanup failure/invalidation preempts prospective success. No callback can reopen CLOSED or change its latched result, revision or reason.

The permanent-closure rule has priority over all recovery rows below. The initiating cancellation/invalidation method and pending public observation receive the triggering outcome/reason with state CLOSED, rather than replacing that first reason with closed. Later method calls return blocked/closed, while snapshot retains the first terminal reason. A stale/wrong-owner/replayed pure rejection does not terminate the current read or close its controller.

No state can resume an old capture.
