## 2. Exact types, budgets and validation

All data schemas below are closed: every listed key is required, no other string or symbol keys, no optional keys or implicit defaults. Alternatives explicitly use `null`. ## 3. Complete enum and result vocabulary

The complete operation enum is `capture`, `attach_review`, `confirm`, `observe`, `complete`, `cancel`, `manual`, `invalidate`, `timeout`, `worker_restart`, `snapshot`. Only `confirm`, `observe`, `cancel`, `manual` are review-intent operations. `complete` and `timeout` are internal events, not exported admission endpoints. Invalid operation strings are never echoed; the public `operation` uses the called method's fixed operation, or `invalidate` for an invalid trusted invalidation event. Unknown review operations produce `operation_unknown`.

Outcomes: `accepted`, `observed`, `rejected`, `blocked`, `cancelled`, `manual`, `invalidated`, `snapshot`. States: `IDLE`, `CAPTURED`, `CONFIRMED`, `READING`, `MANUAL`, `CANCELLED`, `CLOSED`. Role-summary values: `empty`, `supported`. An observed role is a completed historical one-shot summary, not a current binding or authority. There is no aggregate-ready/continuing-success state.

Validation priority is deterministic and applies even while dispatch is busy: (1) CLOSED/latched terminal disposition; (2) actual connection identity or trusted owner-only entry point; (3) inert correlation validation and freshness; (4) remaining closed schema, operation and byte validation; (5) validated terminal action or applicable authenticated fault; (6) busy rejection for nonterminal reentrant mutation; (7) remaining enabled-state, clock/deadline and target/role/capability/page checks for ordinary nonterminal work. Section 6.10 defines the terminal exceptions precisely. A terminal action never needs a new read or a clock callback to revoke admission; an already latched timeout/clock failure still wins. Where a nonterminal operation checks both deadlines, capture_expired wins if both have expired.

For a review call, first require reference equality to the current connection, then inspect only inert descriptors needed to establish the current `bootId`, `reviewId`, `captureId`, `generation` and unused `intentSeq`. Missing/malformed/oversized correlation, stale owner, wrong generation/capture or replay is a pure rejection with the applicable existing schema_invalid/size_exceeded/owner_mismatch/correlation_mismatch/replayed_intent reason; it cannot terminate the current read. Do not inspect the rest of wrong-connection/stale traffic. Only after all correlation matches does an extra key, unknown operation, bad role type or other remaining closed-schema/size fault count as an authenticated current-owner fault and retain the specified fail-closed effect. Matching the connection alone is insufficient. Unknown-operation and wrong-method behavior otherwise keep their existing reason codes. This precedence prevents a stale message with an additional malformed field from invalidating current work.

Trusted review_lost likewise checks its current review/document pair before remaining payload validation: an absent, malformed or obsolete pair has no authority to terminate the current review, even if other fields are malformed. Other trusted lifecycle faults retain their existing fail-closed disposition. Trusted replacement must validate a new allowed sender/connection distinct from current/retired; duplicate or retired attachments remain pure rejections. No public review-intent operation can invoke capture, attachment or lifecycle methods.

Within each validation stage use schema field order, validate descriptors without getters/coercion, and recheck the current generation/terminal latch after reflection. A nested terminal action that commits during validation wins; the outer call cannot later consume its stale ticket or overwrite its reason. Asynchronous completion first checks its private pending identity and CLOSED/RETIRED status; obsolete completions cannot change even readPhase, recorded reason or public sequence. Rejection does not require traversing remaining fields to enumerate faults.

## 6. Correlation, provenance and one-use admission

1. Start empty with immutable boot ID and private instance identity. A real Chrome callback is neither required nor fabricated. The owner-only capture method is the sole synthetic invocation source; a review's claim of invocation is an unknown field and rejected.
2. Attach a validated review sender and fresh connection by the trusted boundary. No caller-supplied generation is authoritative. Same current connection/pair is a duplicate (`replayed_intent`); a retired connection cannot be reattached. Because only two review connections belong to a test scenario, the harness must never reuse them; the controller also rejects a sender matching the immediately retired pair. Additional attachments require a separately initiated test scenario, not an unbounded retired-owner registry or automatic replacement controller. If a valid review replacement would terminate an unsettled underlying read, close the current controller instead: do not install the new owner or issue its ticket.
3. Issue one current ticket on attachment (captureId `none`), capture, confirmation and read admission. Each issuance increments `intentSeq` and replaces the previous ticket; only equality to current sequence is eligible. A consumed/lower sequence is replay; a larger/wrong generation/capture is mismatch. Accepted confirm/observe/cancel/manual consumes its ticket before any boundary callback. Stale or wrong-connection traffic never invalidates the current owner's work. Successful completion clears its ticket and publishes no new ticket: another observation requires a fresh private capture. Ending the review remains possible through trusted review_lost, including when no ticket exists.
4. Capture validates/copies the six target fields. Only a fresh capture being admitted with no unsettled underlying read obtains a new clock reading and capturedAt before publication. One unassigned capture only. Capture of a different unused role's fixed tab after a completed observation retains the previous inert summaries. Capturing a tab already summarized, or recapturing with a live capture but no unsettled underlying read, first globally invalidates the old capture/admission/summaries, advances generation, then accepts the fresh capture if valid. A validated recapture affecting an unsettled underlying read instead closes the controller with target_changed, without a new clock callback, capture, ticket or timer. It never automatically confirms/reads. Invalid capture data causes MANUAL fallback only when no underlying read is unsettled; otherwise the same failure closes the controller.
5. Confirmation requires the current private capture, current owner/ticket and explicit role matching the fixed target tuple. It changes CAPTURED to CONFIRMED and sets the selected role. It does not create a read or renew time. Duplicate roles or wrong role/tab mapping fail closed. Three role summaries can only be obtained from three separate explicit confirmations and reads on distinct synthetic tabs; no inference from URL, title or fixture signature assigns a role.
6. Observation requires CONFIRMED, matching selected role, current unused ticket, no pending admission and no unsettled underlying read, and unexpired capture. Reserve pending identity, increment request sequence, and mark READING before invoking `read(copiedFrozenRequest)`. Issue a new ticket for cancel/manual while reading. Recheck current pending identity after ticket delivery and timer setup, immediately before invoking read; if either invalidated the attempt, do not call read. Set `readPhase:IN_FLIGHT` immediately before entering the boundary function and retain the dispatch busy guard. That guard has the explicit terminal exceptions in section 6.10: validated current-owner cancel/manual, trusted lifecycle invalidation, valid trusted recapture/review replacement and applicable authenticated faults can close synchronously from inside read. They are never rejected merely because dispatch is busy. At most one underlying read may be initiated per controller at a time; no retry/replay/queue. A competing nonterminal observe returns busy without clearing the current read. A subsequent read is eligible only after an earlier underlying settlement has actually been observed by its current handler and its admission has terminated, while the controller remains non-CLOSED.
7. `read` must return a same-realm native Promise. After it returns or throws, check the terminal latch before ordinary return/error handling. If no earlier terminal action committed, a synchronous throw or invalid return cannot prove no work escaped: close with boundary_threw or boundary_shape; a current native rejection observed by its handler ends the SETTLED attempt with boundary_rejected. If synchronous reentrancy already closed the controller, preserve that first outcome/reason: a later synchronous throw is caught and discarded without logging or propagating it, and no boundary_threw result replaces the latch. A returned valid native Promise receives inert fulfillment AND rejection sinks synchronously in the same turn, including if already rejected; their bodies do not inspect payloads, invoke controller/boundary operations, throw or return a rejecting Promise. Any Promise produced by sink registration must also finish without an unhandled rejection. The sinks never register new pending work, update readPhase/revision/reason, issue tickets or reopen. A non-Promise/thenable return after closure is ignored without reading its then getter or replacing the latch with boundary_shape. Never accept arbitrary thenables. Use captured native Promise operations and recheck the latch after potentially reentrant handling. This handles the returned boundary Promise only, not unrelated hidden promises created by boundary code; no physical cancellation or arbitrary-code sandbox is promised.
8. A completion can be admitted only through the closure associated with the exact pending entry. Check CLOSED/retired status and entry/owner/instance/generation before any mutation or payload inspection. A current native settlement handler then sets `readPhase:SETTLED`, checks all envelope IDs, the sole result's captured tab/window/frame/document/origin/URL, capability and page-kind, then clock/deadlines and current state again immediately before consume. There is no result admission by copied request ID alone. A document changed with identical URL fails. Missing lifecycle evidence is not silently inferred; changes known to the harness are explicit invalidation stimuli, not real event coverage.
9. Consume/clear pending and capture, invalidate its ticket, cancel the timer and discard private comparators before publishing a terminal result. Valid settled `supported` with `available` produces one `observed` result and that role's inert summary; a settled `unsupported`, `unknown`, denied/unsupported capability or malformed/rejected result enters MANUAL and clears all summaries. A termination while readPhase is IN_FLIGHT instead sets readPhase RETIRED and state permanently CLOSED, clears all owner/capture/admission/summary data and settles the public observation result with the first terminal reason and state CLOSED. This includes cancellation, manual request, timeout, target/review invalidation, review replacement, recapture and current-owner faults. Later underlying settlement is discarded without inspecting payload, mutating even readPhase/revision/lastReason, issuing a ticket, notifying again or reopening. No result represents continuing freshness or account identity.
10. **Terminal precedence over busy:** while readPhase is IN_FLIGHT, validate entrants in the order specified in section 3 before applying the general busy guard. A current-owner cancel/manual with the current unused ticket, correct operation and null role consumes that ticket and terminates immediately. Valid trusted target_changed/current review_lost/worker_restarted events retain immediate terminal authority. Valid trusted captureInvocation for a recapture terminates with invalidated/target_changed without installing a new capture; valid trusted attachReview replacement terminates with invalidated/review_replaced without installing a new owner or ticket. These owner-only entry points still require their exact schema/corpus/identity checks; a page or review cannot claim their authority through an intent field. Authenticated current-owner schema/size faults retain their terminal failure behavior; unproven, wrong, stale or replayed correlation never acquires terminal authority. Nonterminal reentrant confirm/observe and any other mutation not covered by a terminal rule return rejected/busy without consuming a ticket, changing revision or invoking the boundary. Snapshot remains read-only. Outside IN_FLIGHT, the existing non-reentrant transition rules apply; trusted lifecycle invalidation can still terminate immediately, while other reentrant mutations remain busy.

For each authorized termination, recheck current owner/generation/latch immediately before commit, then synchronously set CLOSED/RETIRED, latch the first terminal outcome/reason and invalidate all admission authority before invoking cleanup callbacks. Settle the public observation exactly once with that latched outcome and state CLOSED; cleanup failures or nested later calls cannot replace it. The commit has no await or external callback between its latch/state/admission updates. Clear current ticket, pending admission, owner and private comparison references; publish no replacement. The original outer read invocation must inspect this latch before every subsequent mutation/notification, including its return/throw path. First means the first validated termination to commit, not an unvalidated caller's claimed intent. Review harness actions normally occur after ticket delivery returns; the mandatory reentrancy tests deliberately exercise these exceptions inside boundary.read. CLOSED clears all owner/retired identities, summaries and operational handles, cannot accept captures/reviews/observations, and has no reset/reopen path.

The externally held Promise, boundary request copy or queued reaction may outlive these cleared references. At most one retired underlying read can remain associated with this permanently closed controller because it can never initiate another. External manual fallback remains non-authorizing. Creating another controller is not an automatic retry/recovery mechanism; this per-controller rule provides no cross-instance browser-operation bound or production cancellation guarantee.

Terminal rows consume pending admission before notifying any external callback; admission rows instead reserve it before calling the boundary. “Clear” means capture, pending, ticket, timer and all summaries unless a row expressly retains summaries. Each accepted capture/review replacement/global invalidation advances generation and synchronizes any surviving Owner.generation; every accepted mutation increments revision. Ordinary confirm/read advances ticket sequence without renewing capture time; success clears the ticket. `terminalLatched` records the first terminal outcome/reason and is not set by intermediate capture/confirmation/admission. The existing busy field remains true during the outer boundary invocation; it is a nonterminal dispatch guard, not a veto on validated section 6.10 terminations. Early termination atomically sets CLOSED/RETIRED, latches its result and clears admission before cleanup callbacks; the outer dispatch's later return, catch or finally must not reset private state, counters, owner, tickets or the latch after closure. Settled success is published only after cleanup; a cleanup failure/invalidation preempts prospective success. No callback can reopen CLOSED or change its latched result, revision or reason.
