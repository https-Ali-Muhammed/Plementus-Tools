## Automatic cleanup contract

1. Register an event-driven worker listener at module evaluation and create one private service initialization promise on the first relevant worker execution. A supported startup event may request initialization and cleanup; the first checkpoint request must also do so. Browser launch, worker activation and service execution are different events. Chrome/Brave launch alone does not prove that the worker ran. A closed browser, stopped device or worker that receives no event cannot delete records. The earliest *permitted execution* means the first actual service execution after expiry, not a guaranteed wall-clock deadline.
2. Before `create`, `read`, `transition`, `delete`, recovery lookup or any future checkpoint-dependent operation, enter a service-owned cleanup gate. No caller may call the repository or IndexedDB directly. Concurrent requests in one worker share in-flight initialization/cleanup; they await transaction completion, then each applies its own authorization, schema, state, revision and fresh-time checks. A successful gate is scoped to that access, not cached for the worker lifetime. A failed gate rejects all waiting requests with one generic failure; later attempts may retry cleanup, but no failed request proceeds automatically.
3. Sample and validate time before the cleanup scan. With uncertain time, unavailable storage, malformed/legacy records, conflict or abort, fail closed and expose only a generic result. Do not infer an expiry date for legacy data or delete invalid/unknown records. Preserve them for owner-authorized resolution; block checkpoint use while their presence prevents a complete cleanup pass. Preserve forensic context only through separately authorized, sanitized handling.
4. In a single IndexedDB `readwrite` transaction, inspect each stored record, require the exact seven-field v2 structure and matching key, classify expiry, and delete only structurally valid expired rows. The same transaction either commits the whole scan/deletion set or aborts it. A cursor/delete race, changed revision or unexpected record aborts; do not skip it or report a partial success. Where a competing context can write, compare the revision observed for each deletion within the transaction; IndexedDB transaction serialization is the final arbiter across contexts and worker restarts. Never rely on an in-memory mutex alone.
5. Resolve the gate only on `transaction.oncomplete`. On abort, error, blocked opening or uncertain completion, report failure without a record or raw error. A subsequent fresh transaction may check that deleted keys are absent where feasible; absence is useful evidence, not forensic erasure. A failed absence check keeps the outcome unresolved and blocks use. Do not report deletion on a queued request's success callback alone.
6. After the gate, perform the requested operation in its own guarded transaction and recheck time and eligibility immediately before reading for recovery or committing a mutation. If the clock crosses the expiry boundary during an await, abort/deny. Revision and expected-state checks remain atomic with the write or authorized delete. `createdAt` is copied unchanged. Completed/cancelled acknowledgment deletion and explicit operator deletion keep their separate authorization and expected-revision checks. An expired checkpoint never reaches recovery, transition or external action code.

The worker should expose only named, sender-validated operations through a narrow request schema. Its popup may request the service; content scripts and untrusted pages receive no database handle or direct access. Remove or make inaccessible the v1 repository `update` path before production integration, or guard it equivalently. No generic record-update message, automatic provisioning, retry, provider call, sync, export, telemetry, sensitive persisted field, new permission or external request follows from this design. An uncertain external action stays `reconcile_required` pending a separately approved operator reconciliation path; startup cleanup never replays it.

## Clock-safety analysis and owner decision

The seven persisted fields remain exactly `schemaVersion`, `runId`, `state`, `step`, `evidenceTier`, `revision`, `createdAt`. `createdAt` is a finite, safe integer set once at creation, never rewritten by updates. A trustworthy injected current time `now` must be finite, safe, nonnegative and at least `createdAt`; check `createdAt + 604800000` for safe range. Logical expiry begins at `now >= createdAt + 604800000`, including equality. This rule gives exactly seven days only if the clock is trustworthy. A future timestamp, invalid timestamp or unavailable clock blocks use. Test injection verifies logic but is not a trusted production clock.

| Condition | Browser-only mitigation and safe result | Remaining limit |
|---|---|---|
| Clock moves backward during one worker lifetime | Compare each wall-clock sample with the previous sample; a decrease blocks cleanup and checkpoint use. A monotonic `performance.now()` elapsed-time comparison can detect larger disagreement within that worker, with an owner-approved tolerance. | Worker suspension/restart resets process-local observations; clock and monotonic sources may be unavailable or inconsistent. |
| Clock rolls back across worker/browser restarts | On restart, reject malformed/future `createdAt`; require a new trust decision before use when elapsed time cannot be established. | The seven fields contain no trusted last-observed time. A plausible rolled-back wall clock can make an expired checkpoint appear eligible. Local storage or an added persisted high-water mark is editable and is not approved in this schema. No reliable browser-only proof of elapsed time exists across restarts. |
| Clock jumps forward | Compare wall time with monotonic elapsed time during a worker lifetime; unexpected disagreement blocks use **and deletion** pending review. | Without trusted external time, a forward jump across restart can cause premature expiry/deletion. A tolerance is an owner/security policy decision, not an established value. |
| Offline or time synchronization changes | Offline operation may continue only if the chosen local time-trust policy says observations remain trustworthy; detectable sync jumps block. | Network absence does not make the OS clock correct. An external time service is neither approved nor required by this design. |
| Browser reopens after the seven-day date | At first actual service execution, attempt cleanup before access if time is trusted; deny expired recovery. | A closed browser cannot delete at expiry. If time is untrusted on reopening, block use and deletion until owner-authorized resolution; physical bytes may remain. |
| Time unavailable or untrusted | Fail the cleanup gate and all checkpoint-dependent operations. Report a generic blocked state for operator review; do not replay work. | This may prevent Option B deletion at the next execution. The owner/security reviewer must decide a clock-trust and remediation policy before activation. |

Browser-only choices for owner/security review are: (A) accept the residual restart-clock risk under documented device and operator controls; (B) fail closed after a restart whenever time cannot be trusted, with an authorized manual resolution process; or (C) keep activation blocked. The owner may request a later schema/policy amendment for additional local evidence, but such evidence alone cannot establish trusted elapsed time against a changed OS clock. This design adds no field and approves no remote time source. The owner/security reviewer must choose how trust is established, how discrepancies are handled, whether any tolerance is acceptable, and how blocked expired records are resolved. Until then the clock gate remains **OPEN**.

## Option B retention and safety limits

Logical expiry is exactly seven days after immutable creation; updates never slide it. Physical deletion is attempted at the next actual permitted extension execution after expiry, including startup/access, before checkpoint use. If Chrome/Brave remains closed, bytes may persist beyond seven days until that execution. Failed cleanup blocks use. IndexedDB deletion and subsequent absence do not prove forensic erasure from browser files, snapshots or backups. Neither cleanup nor recovery automatically retries an uncertain provider action.
