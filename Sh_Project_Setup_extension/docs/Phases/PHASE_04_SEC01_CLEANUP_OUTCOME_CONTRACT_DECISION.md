## Current cleanup transaction and failure path

1. In [`checkpoint-service.mjs`](../../src/storage/checkpoint-service.mjs), `gate()` assigns `cleanupInFlight ??= cleanupPass()`. `cleanupPass()` first calls `time()`; a detected invalid, backward, regressing, too-wide, or excessive-forward sample latches `clockBlocked` and rejects **before a transaction begins**. This is a blocked no-transaction outcome, not `VERIFIED_ABORTED`.
2. With an accepted starting sample, `cleanupPass()` opens one `readwrite` transaction and scans the whole checkpoint store. Each cursor row must have a known same-instance creation bracket, matching key and valid seven-field structure. `eligibilityFor()` applies the captured starting sample to exact wall expiry and the conservative same-instance monotonic lower bound; disagreement latches uncertainty. For an expired row, `cursor.delete()` is requested and its ID is appended to a local `deleted` array before the delete request or transaction has completed. Any row failure aborts the whole pass; the array alone proves no deletion.
3. At cursor exhaustion, `done(deleted)` sets the transaction's pending result. `transaction()` resolves it only from `tx.oncomplete`, after commit; `tx.onabort` or `tx.onerror` rejects generically. The fake stages writes until its commit point, then calls `oncomplete`; its paused-commit snapshot is unchanged, its committed snapshot lacks the row, and its explicit abort restores the unchanged row. The fake cannot prove a real-browser commit or simulate lost completion.
4. After `await pass`, each `gate()` caller removes every returned ID from its **volatile** `known` map, then calls `time()` again, then returns `deleted.length`. If that post-commit sample detects an anomaly, it latches `clockBlocked` and throws after the transaction has committed and after `known` was updated. The caller receives no count. Deleting `known` entries is not persisted obligation tracking or physical absence proof.
5. Every public `create`, `read`, `transition`, `delete`, and `cleanup` call passes through `safe()`, which catches this failure and an abort alike and throws only `Checkpoint operation failed`. `create`, `read`, `transition`, and `delete` cannot continue to their own transactions if their gate rejects. The error neither proves a retained row nor discharges a deletion obligation.
6. Concurrent operations share the same `cleanupInFlight` **transaction promise**, not one indivisible gate result. Each awaiting caller separately updates `known`, samples post-commit time, and may settle independently. Each `finally` clears `cleanupInFlight` only if it still references that pass. A late entrant or worker interruption can therefore have different observation evidence; duplicate count reporting or one caller's success must not authorize another caller's work or clear a global block. A rejected pass clears the shared reference, but an ordinary abort without a clock latch can be followed by a fresh guarded attempt; this is not replay of a possibly committed operation.

## Candidate internal diagnostic outcomes

These labels describe evidence **inside a future reviewed cleanup/reconciliation design**. They are neither approved public API responses nor new persisted checkpoint fields. A generic public rejection cannot by itself select one. Apply classifications per guarded pass and affected row set; do not infer a whole-store outcome from one row's observed absence.

| Outcome | Minimum evidence and consequence |
|---|---|
| `VERIFIED_COMMITTED` | Authoritative `tx.oncomplete` for the guarded pass, validated target/delete request set, and no *observed* clock rejection through the required post-commit check. This establishes transaction completion only. It does **not** prove the clocks were sound throughout the asynchronous gap, deletion was safe under policy, forensic erasure, or discharge of an owner-controlled obligation. |
| `VERIFIED_ABORTED` | Authoritative transaction-abort evidence before commit, with atomic unchanged-record verification where feasible. A staged delete, `tx.onerror` alone, generic rejection, or missing callback is insufficient. Keep the obligation open; apply the existing global gate and clock latch independently. |
| `OUTCOME_UNKNOWN` | Completion signal or target evidence is missing, contradictory, lost on worker termination, or otherwise insufficient to prove commit or abort. Preserve the obligation, block use and fresh work, and require guarded owner-controlled reconciliation. Never auto-retry or infer an abort from a rejected promise. |
| `COMMITTED_BUT_CLOCK_UNCERTAIN` | Authoritative commit evidence exists, but an observed clock anomaly during the pending interval or at the post-commit sample latches uncertainty. Preserve both facts: the deletion committed, while its safety/retention disposition remains unresolved. Block all dependent work; no success or old-record absence may be treated as authorization. |

Clock failure before transaction creation is separately **NO_TRANSACTION / CLOCK_BLOCKED** for diagnostic reasoning, without changing the public generic error. If a clock fault occurs during commit but is unobservable at all samples, a nominal `VERIFIED_COMMITTED` classification cannot prove safety; the observation gap below remains a security acceptance blocker. A committed deletion cannot be undone by relabeling it uncertain.

## Remediation approaches for owner/security decision

| Approach | Backward compatibility and fail-closed behavior | Privacy, races, unknown completion, and physical retention |
|---|---|---|
| **A. Keep generic public errors; separately retain verified transaction outcome through an authorized, sanitized reconciliation process.** | Least public contract change. All public callers still reject on clock uncertainty and cannot continue. The diagnostic channel must distinguish commit, abort, and unknown without letting a generic error mean “unchanged.” An in-memory result alone disappears with the worker and cannot discharge an obligation. | Owner/security must authorize where a minimal outcome/obligation record lives, who can inspect it, its lifecycle, and how it is reconciled without a new checkpoint field, telemetry, export, raw error, sensitive ID, or unauthorized storage. Correlate concurrent callers to one pass and distinguish pass completion from each caller's post-check. Lost callbacks or termination remain `OUTCOME_UNKNOWN`; a verified commit still needs reviewed safety and feasible absence evidence before any obligation is closed. |
| **B. Return a reviewed, explicitly blocked structured *internal* result for committed-but-uncertain cleanup.** | Could make the known commit visible to guarded internal callers, but changes their contract and every caller must prove that a blocked result never becomes permission to create, read, transition, delete, resume, or admit a fresh run. Keep public errors generic unless separately approved. A committed count cannot be interpreted as operational success. | Limit the structure to sanitized transaction evidence and a blocking state, with no row contents or raw error. Define one shared-pass result plus per-caller clock checks so races cannot produce a permissive result. Worker death before delivery remains `OUTCOME_UNKNOWN`. A volatile structure does not satisfy outstanding physical-retention tracking; owner-controlled reconciliation and absence checks are still needed. |
| **C. Withhold automatic expiry deletion until sufficient clock and transaction assurance exists.** | Strongest immediate protection against an unsafe automatic delete and avoids the post-commit deletion/error ambiguity for that path. It changes the owner-approved normal rule to attempt deletion at the earliest permitted execution when time is sound, so it requires an explicit **policy and product decision** before implementation. The strict global gate still blocks checkpoint-dependent work; no retention-based bypass follows. | More records remain physically present, potentially indefinitely under the approved uncertainty exception; device/profile controls and an owner-controlled outstanding-obligation process become more urgent. Explicit owner-approved destructive disposition remains case-specific. Withholding does not resolve existing interrupted transactions, unknown outcomes, or real clock assurance. |

For **each** approach, `tx.oncomplete` is evidence of database transaction completion, not evidence that the clock was trustworthy at deletion time or that a physical-retention obligation is discharged. An unchanged record after verified abort remains an obligation; an absent row after a known commit still requires a reviewed disposition; a missing completion signal stays unknown. IndexedDB deletion is not forensic erasure.

## Asynchronous commit observation gap

The current candidate samples before the transaction and after completion. Clock movement can occur after the first sample while IndexedDB work is pending; the post-commit sample can detect some movement only **after** deletion is irreversible. Another `time()` call immediately before requesting `cursor.delete()` or commit would leave a later interval until actual commit, and a clock fault could change and revert between samples. Worker suspension or termination can also remove the completion observation. Therefore one more sample cannot guarantee clock safety or transform `oncomplete` into elapsed-time proof. Owner/security must explicitly accept a bounded supported-environment assumption with evidence, or choose a different policy/product scope. The existing 1 ms bracket, 1.1 ms detection allowance, 0.1 ms expiry subtraction, exact seven-day rule, and latched response remain unchanged pending that decision.
