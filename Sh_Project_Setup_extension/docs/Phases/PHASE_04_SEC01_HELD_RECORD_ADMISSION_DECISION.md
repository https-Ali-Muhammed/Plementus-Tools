## Decision summary

**BLOCKED_REQUIRES_POLICY_OR_TRUST_DECISION.** A complete guarded scan can preserve a valid restart-uncertain row and complete cleanup of rows whose expiry is established. It cannot, under the present wording, prove that cleanup of the held row is complete or that it is not due. The [SEC-01 policy](PHASE_04_SEC01_APPROVED_POLICY.md) and [Option B](PHASE_04_SEC01_RETENTION_AMENDMENT_B.md) require cleanup before checkpoint-dependent operations; the [uncertain-time exception](PHASE_04_SEC01_UNCERTAIN_TIME_RETENTION_AMENDMENT.md) permits an outstanding local hold but does not expressly authorize fresh admission beside it. An owner/security amendment must define that narrow case. Separately, the seven-field checkpoint has no target identifier, and this repository has no demonstrated independent evidence chain that binds the old `runId` to an exact target or excludes pending effects. Operator assertion, a plausible clock, and a fresh approval cannot fill that gap.

The smallest safe current action is to retain the old row blocked with its outstanding retention obligation, reconcile possible external effects through an authorized route, and keep fresh checkpoint creation blocked. If a separately reviewed, case-specific manual deletion later meets the existing owner-only rules, ordinary fresh-work authorization can be considered after that disposition; deletion must not be used as an admission shortcut. No automatic replay, uncertain expiry deletion, direct IndexedDB edit, or v1 repository bypass is permitted.

## Classification: `HELD_UNCERTAIN` is custody, never eligibility

Classify an old row as `HELD_UNCERTAIN` only when **all** of these hold:

1. A full guarded scan reads the row from the sole checkpoint store; its primary key matches a valid `runId`; the exact seven-field v2 structure and values validate. Its observed `runId` and `revision` can be bound to the owner-controlled case without exposing the checkpoint. No migration, repair, inferred creation time, or field addition occurs.
2. Expiry cannot be established with accepted evidence because the original service-instance creation bracket was lost across an unobserved worker/browser lifetime gap, or accepted clock evidence has become uncertain. A plausible `Date.now()`, a new monotonic origin, and the stored `createdAt` do not restore that evidence. The row is **not** called eligible or expired from its wall timestamp alone.
3. No trusted same-instance evidence already establishes expiry. If it does, the row is **expired** and Option B cleanup is due; it cannot be relabeled held to avoid deletion. A row with valid current same-instance evidence below the boundary is **eligible** only under the normal policy, not held.
4. The scan has no malformed/legacy/unknown-version row, key mismatch, transaction failure, or stale case/revision binding. Such conditions are distinct blockers. An invalid or unavailable clock may justify retaining a structurally valid row as uncertain custody, but it blocks the entire admission attempt; it is not a successful cleanup pass.

`HELD_UNCERTAIN` is an operational classification outside the seven persisted fields. The stored `state` remains unchanged even if it says `ready`, `running`, or `completed`; the old run may not read for continuation, transition, authorize, replay, retry, or receive a refreshed `createdAt`. A held record remains physically present and carries an outstanding retention obligation. A later trusted-time result, guarded disposition, or incident hold must be re-evaluated; the label never becomes a durable exemption.

## Conditional admission contract: preconditions and postconditions

These are **proposed necessary conditions**, not current permissions. Every condition must be demonstrable for **every** held row and every possible effect before a fresh run can be admitted:

| Condition | Required proof at decision time |
|---|---|
| Retention custody | An approved sanitized owner-controlled case acknowledges each exact old row/revision, its outstanding physical-retention obligation, prior cleanup status, and any incident-evidence hold. The hold cannot disappear when a new run starts. Trusted expiry still invokes the earliest permitted cleanup; uncertain expiry never causes automatic deletion. |
| External effects | An authorized reconciliation route establishes the outcome and exact scope of each possible old external write, including pending or delayed effects. Unknown, conflicting, or merely attested outcomes block. No old action is replayed. |
| Non-overlap | Accepted independent evidence binds the old run to its exact target/action scope and shows the proposed new target/action and any other active run cannot overlap or conflict, including delayed effects. Distinct `runId`s alone prove nothing. |
| Current context | Independently reverify the active account, exact origin, tab, target/project, environment, permissions, intended effect, and their binding to the requested new action. Recheck after navigation, context change, or restart. |
| Authority and approval | Verify real operator identity and the authority for the particular new action through an approved, revocable, request-bound mechanism. Obtain fresh action-specific authorization; neither old approval, operator reconciliation, a generic continue click, nor old-record deletion approval suffices. The project owner alone retains destructive disposition authority. |
| New record and clock | Validate a distinct unused v4 UUID `runId`, exact v2 seven-field shape, revision `0`, permitted initial state/step/evidence tier, and immutable `createdAt` anchored to a fresh accepted wall/monotonic bracket in the new service instance. Accepted numerical clock criteria and the trusted execution path are prerequisites; a new bracket cannot validate the old row's elapsed time. |
| Storage gate | Complete the database-wide guarded scan and any due trusted-time deletion before admission; recheck classifications, old revisions, case bindings, duplicate ID, approval/context freshness, and no-bypass guarantees in the serialized admission path. Any missing proof blocks. |

On a successful **future** admission, exactly one separate new checkpoint exists with new identity, revision `0`, and its own creation anchor. Every held row is byte-for-byte unchanged, blocked for old-work use, and still associated with an outstanding retention obligation and incident hold. The committed cleanup outcome is reported accurately. Admission grants no permission for an external write; each later action has its own current-context and approval checks. Subsequent checkpoint-dependent operations rerun the cleanup/classification gate and cannot reuse this admission result.

## Non-overlap evidence and provenance

The persisted row has no target. A verified chain would need an **independently existing**, authorized, sufficiently precise source that binds the old `runId` or a reliably correlated case to the exact old account, target, environment, action, and possible delayed effects; a separately verified current observation must establish the proposed new scope. The reviewer must accept the source, correlation method, freshness, completeness, and privacy handling. An authorized read-only provider audit/state observation could contribute **only if** it actually exposes those facts and the old-run binding can be proved; no provider capability or trusted behavior has been demonstrated here. A pre-existing approved owner-controlled case record could contribute **only if** its provenance and binding predate the uncertainty and are independently verifiable. This proposal authorizes neither checkpoint export nor new persisted target metadata.

An operator's memory, checkbox, typed target name, screenshot, current page alone, or claim that the new target is different is an **assertion**, not proof of the old binding or absence of delayed writes. A current provider state showing no visible result does not prove a possible write failed or cannot complete later. If independent binding and bounded effect scope cannot be established within the approved privacy rules, non-overlap is **unknown** and admission is **BLOCKED**. The current repository and cited bounded tests do not demonstrate such a chain.

## Fail-closed decision table

| Observation | Required result |
|---|---|
| Missing old row or new ID collision | Reconcile the changed case; reject stale admission. Never treat disappearance as confirmed deletion without committed transaction/feasible absence evidence. |
| Corrupt, legacy, unknown schema, extra field, invalid `createdAt`, or key mismatch | Abort admission and automatic cleanup for that scan; retain evidence. A separately reviewed disposition procedure is required; do not promote to held, repair, migrate, or infer expiry. |
| Trusted eligible row | Apply normal guarded policy; it cannot inherit a held exception. If active work may overlap, block until independently excluded. |
| Trusted expired row | Delete through the due guarded cleanup transaction before use; conflict, abort, or unverified completion blocks. Do not admit while a due deletion is outstanding. |
| Valid restart-uncertain row | Retain as `HELD_UNCERTAIN` only under the classification above; old-run use remains blocked. Fresh admission additionally needs the proposed policy delta and every admission proof. |
| Missing identity, authority, approval, case obligation, or incident-hold clearance for the proposed action | Reject admission; retain old row and obligation. An incident hold is never overridden by fresh-run approval. |
| External write unresolved, old/new target overlap, or overlap unknown | Reject admission and all retry/replay; seek authorized reconciliation or owner/security decision. |
| Stale old revision, changed case binding/context, concurrent request, or approval revoked | Abort/reject and rescan on a new request. Never reuse a prior approval or pass result. |
| Invalid/uncertain time, cleanup error/conflict, or transaction abort | Reject admission; retain held row and obligation. Do not report deletion or new-run success. A clock correction does not clear a latched uncertainty. |
| Worker/browser restart or tab/context change between reconciliation and admission | Invalidate volatile evidence and approval binding; re-reconcile/reverify under a new request. A restarted service cannot inherit the previous clock bracket. |
| Commit succeeds but response or absence check is uncertain | Do not retry insertion or claim failure left no row. Freeze the candidate new run, re-read/reconcile its exact ID under the guarded path, and keep all old obligations open. |

## Proposed policy delta and transaction ordering

The exact compatibility issue is [SEC-01, “Approved checkpoint policy” and “Proposed implementation contract”](PHASE_04_SEC01_APPROVED_POLICY.md): cleanup before checkpoint-dependent operations and fail-closed cleanup error/conflict; [Option B, “Owner-approved retention rule”](PHASE_04_SEC01_RETENTION_AMENDMENT_B.md): attempt physical deletion of an expired row before such operations. The [uncertain-time exception](PHASE_04_SEC01_UNCERTAIN_TIME_RETENTION_AMENDMENT.md) permits a blocked hold when expiry cannot safely be established, but says nothing affirmative about admitting a new checkpoint while that obligation remains. A complete scan **does not currently suffice as admission authorization**. Treating a held row as if cleanup succeeded would silently amend those clauses.

**Narrow proposed addition for owner/security review, not approved:** “For admission of a distinct fresh run only, a completed database-wide guarded cleanup scan may count as the required pre-operation cleanup when every row with established expiry has been deleted with transaction completion, and every structurally valid row whose expiry remains unprovable is retained blocked as `HELD_UNCERTAIN` with an acknowledged outstanding physical-retention obligation. This limited result permits admission only after independently verified reconciliation, non-overlap, current context, identity, and fresh action-specific authorization. It neither declares the held row cleaned/eligible nor relaxes cleanup failure, conflict, old-run use, incident hold, manual-deletion authority, or later-operation gates.” If the owner/security reviewer does not accept that interpretation and its evidence process, the global block remains.

For a future disconnected implementation, obtain and validate external evidence **before** entering IndexedDB; asynchronous provider or identity calls must not be awaited inside a transaction. The sole guarded service should serialize requests and use one `readwrite` transaction spanning a full cursor scan, any trusted-due deletions, old-row revision/key rechecks, duplicate-ID check, and new-row insert. The approved evidence/authorization mechanism must yield a request-bound, fresh, synchronously checkable decision at the transaction boundary; if it cannot, admission is blocked. IndexedDB serialization must cover competing admission, cleanup, and disposition in the same store, with stale revisions and changed row sets aborting. A scan that commits before a separate insert is insufficient if another request can change the case between them.

Take an accepted fresh wall/monotonic bracket at creation in the new service lifetime; set `createdAt` once from that sample, then validate it and the immutable seven-field record before insertion. Recheck time at the last safe point before transaction commit; any uncertainty aborts. The old row's lost bracket is never reconstructed from this sample. No delete or insert is reported before `tx.oncomplete`; an abort commits neither. If completion is ambiguous after the transaction may have committed, block and reconcile the new ID instead of retrying. The current 1.1 ms forward-detection allowance, 1 ms bracket cap, 0.1 ms precision assumption, and same-instance expiry criterion remain unaccepted for production; this document does not approve them.

Manual old-record deletion remains a **separate** case-specific disposition. When expiry cannot be established, only the verified project owner may approve it; no delegation. Require the existing reliable identity/target/revision evidence, incident-evidence handling, guarded transaction completion, and feasible absence verification. Fresh-run approval cannot authorize deletion, and deletion approval cannot authorize fresh work.
